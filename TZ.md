# Техническое задание
## AgroTechno

### 1. Общие сведения

AgroTechno предназначена для создания, ручного назначения и контроля рабочих задач сельскохозяйственного предприятия. Руководитель планирует работы и контролирует результаты, а работники просматривают задания и фиксируют выполнение своей части работы.

Цель разработки — создать учебный MVP с централизованным хранением задач, сроков, назначений и результатов. Доступ к системе осуществляется через веб-браузер.

| Параметр | Значение |
| :--- | :--- |
| Заказчик | Сельскохозяйственная фирма «Агро-Техно» |
| Платформа и масштаб | Веб-приложение, учебный MVP |
| Назначение исполнителей | Только вручную руководителем |
| Виды задач | Индивидуальные и групповые |
| Серверная часть | Go (Golang), единое серверное приложение |

### 2. Роли и права доступа

| Операция | Руководитель | Работник |
| :--- | :--- | :--- |
| Вход и выход | Да | Да |
| Просмотр задач | Все задачи | Только назначенные |
| Создание и редактирование | Да | Нет |
| Назначение и снятие исполнителей | Да | Нет |
| Изменение индивидуального статуса | Нет | Только своего |
| Подтверждение и отмена задачи | Да | Нет |
| Общая сводка и история | Все задачи | Свои задачи |

Предлагаемое разграничение для MVP: руководитель управляет задачами, а исполнителями являются пользователи с ролью «Работник». Учётные записи и справочники предварительно создаются при настройке учебного стенда.

### 4. Статусы и бизнес правила

#### 4.1 Индивидуальный статус назначения

| Статус | Условие и допустимый переход |
| :--- | :--- |
| Не начата | Начальное состояние. Исполнитель может перейти в «В работе». |
| В работе | Исполнитель начал работу. Может перейти в «Завершена». |
| Завершена | Исполнитель зафиксировал завершение и при необходимости комментарий. Обратный переход в MVP не предусмотрен. |

#### 4.2 Общий статус задачи

| Статус | Правило |
| :--- | :--- |
| Не начата | Все действующие назначения имеют статус «Не начата». |
| В работе | Есть начавший или завершивший работу исполнитель, но не все действующие исполнители завершили работу. |
| Ожидает подтверждения | Все действующие исполнители имеют статус «Завершена». |
| Выполнена | Руководитель подтвердил задачу в состоянии «Ожидает подтверждения». |
| Отменена | Руководитель отменил ещё не выполненную задачу. |

Правила одинаковы для индивидуальных и групповых задач. «Выполнена» и «Отменена» — конечные состояния: изменение задачи, назначений и индивидуальных статусов запрещено. Возврат на доработку и принудительное закрытие до завершения всех назначений в предложенный MVP не входят.

#### 4.3 Признак просрочки

«Просрочена» — вычисляемый признак, а не статус. Он включается, когда текущий момент позже планового срока окончания, а общий статус не равен «Выполнена» или «Отменена». Ожидающая подтверждения задача также может быть просроченной. Это правило учитывает время ожидания руководителя и требует согласования.
Для полей, содержащих только дату, предлагается считать срок истёкшим с 00:00 следующего дня.

#### 4.4 Изменение состава исполнителей

Предлагается разрешить изменение состава до подтверждения или отмены. Новый исполнитель получает статус «Не начата». Снятое назначение сохраняется как недействующее вместе со статусом, датами и комментарием; оно исключается из расчёта общего статуса и прогресса. Снятие последнего действующего исполнителя запрещено.

После изменения состава статус пересчитывается. При добавлении нового работника к ожидающей подтверждения задаче она возвращается в «В работе». Статусы оставшихся работников сохраняются. Повторное назначение снятого исполнителя в этой версии не предусмотрено; его правила следует согласовать отдельно.

### 5. Данные и архитектура

Приложение строится по клиент-серверной архитектуре. Фронтенд работает в браузере пользователя и обращается к серверу через REST API. Бэкенд реализуется на языке Go (Golang): он проверяет права, выполняет бизнес-логику и работает с централизованной реляционной базой данных. Для учебного MVP используется одно серверное приложение с логическим разделением кода на модули.

#### 5.1 Сущности данных

| Сущность | Основные данные |
| :--- | :--- |
| Роль | Идентификатор, наименование: руководитель или работник. |
| Сотрудник | Идентификатор, ФИО, уникальный логин, хеш пароля, ссылка на роль. |
| Участок | Идентификатор и наименование участка. |
| Тип работы | Идентификатор и наименование: посев, полив, обработка почвы, уборка урожая и другие. |
| Рабочая задача | Идентификатор, название, описание, участок, тип работы, плановые даты, общий статус, создатель, дата создания, дата подтверждения и подтвердивший руководитель. |
| Назначение задачи | Идентификатор, задача, сотрудник, дата назначения, индивидуальный статус, фактическое начало и завершение, комментарий, признак действующего назначения, дата снятия. |
| История изменений | Идентификатор, задача, при необходимости назначение, тип события, прежнее и новое значение, автор, дата и время. |

#### 5.2 Связи и ограничения

Каждая задача связана с одним участком и одним типом работы. Сотрудник может иметь несколько задач, задача — нескольких сотрудников. Связь многие ко многим реализуется через сущность «Назначение задачи». Задача и назначение могут иметь несколько записей истории.

Пара «задача — сотрудник» уникальна. У незавершённой неотменённой задачи должно быть минимум одно действующее назначение. Ссылки на сотрудников и справочники должны сохранять целостность данных. Для завершённой задачи обязательны дата подтверждения и руководитель, подтвердивший выполнение.

Изменение назначения, пересчёт общего статуса и запись истории должны выполняться согласованно в одной транзакции. Сервер проверяет актуальное состояние перед подтверждением, чтобы одновременное добавление исполнителя не позволило закрыть незавершённую задачу.

#### 5.3 Основной сценарий

Руководитель создаёт задачу и назначает работников. Каждый исполнитель видит её в своём списке, начинает и завершает свою часть работы. Когда все завершили работу, задача ожидает подтверждения. Руководитель проверяет результаты и подтверждает выполнение. Система сохраняет историю и включает задачу в сводку.

#### 5.4 Клиентская часть веб-приложения

Фронтенд обеспечивает отображение задач и выполнение доступных пользователю действий. Для небольшой первой версии предлагаются HTML, CSS и JavaScript без обязательного использования отдельного фронтенд-фреймворка. Интерфейс состоит из нескольких страниц с общей навигацией; сложное одностраничное приложение не требуется.

| Экран | Содержание и доступные действия |
| :--- | :--- |
| Вход | Поля логина и пароля, кнопка входа и сообщение об ошибке. После входа открывается список задач пользователя. |
| Задачи руководителя | Общий список задач, фильтры по статусу, исполнителю, участку и типу работы; кнопка создания задачи. Здесь же размещается краткая сводка по статусам и выполнению за период. |
| Мои задачи работника | Назначенные индивидуальные и групповые задачи, личный и общий статусы, сроки и признак просрочки; фильтры по личному статусу и сроку. |
| Карточка задачи | Описание, участок, тип работы, сроки, исполнители, их статусы, прогресс и история. Работник начинает и завершает свою часть с комментарием; руководитель редактирует, отменяет или подтверждает задачу по правилам раздела 4. |
| Создание и редактирование | Одна форма для руководителя: название, описание, участок, тип работы, даты и выбор исполнителей. Сотрудники и справочники загружаются с сервера; отдельный экран управления ими не требуется. |

На компьютере задачи отображаются таблицей, на узком экране допускается представление карточками. Статусы обозначаются текстом; цвет используется как дополнительный признак. В навигации отображаются имя пользователя, доступные разделы и кнопка выхода.

Фронтенд проверяет заполнение обязательных полей и порядок дат для удобства пользователя. Окончательную проверку выполняет сервер. Во время запроса отображается состояние загрузки, повторная отправка формы блокируется. При ошибке показывается понятное сообщение, введённые данные сохраняются в открытой форме. Об успешном сохранении сообщается только после ответа сервера.

#### 5.5 Серверная часть на Go

Бэкенд представляет собой единое HTTP-приложение на Go. Для приёма запросов может использоваться стандартный пакет `net/http`. Код разделяется на обработчики HTTP-запросов, слой бизнес-логики и слой доступа к базе данных. Такое разделение упрощает разработку без создания отдельных сервисов.

Обработчики принимают запросы, проверяют формат входных данных и передают их бизнес-логике. Модуль авторизации проверяет логин и пароль, создаёт сеанс и определяет текущего пользователя. Во всех защищённых операциях сервер проверяет роль, доступ к задаче и принадлежность изменяемого назначения.

Бизнес-логика создаёт и редактирует задачи, управляет назначениями, проверяет допустимые переходы статусов, рассчитывает общий статус и прогресс, подтверждает и отменяет задачи. Общий статус и автор изменения определяются сервером. Работник не может передать чужой идентификатор и изменить результат другого исполнителя.

Слой доступа к данным выполняет параметризованные запросы к реляционной базе. Связанные изменения назначения, общего статуса и истории сохраняются в одной транзакции. Если операция не выполнена полностью, изменения откатываются. Состав сущностей и ограничения данных приведены в подразделах 5.1 и 5.2.

Сервер формирует списки и фильтры с учётом прав пользователя, возвращает историю и базовую сводку. Признак просрочки вычисляется при получении данных по правилу подраздела 4.3; отдельная фоновая служба для этого не требуется. В журнал записываются технические ошибки без паролей и идентификаторов сеансов.

#### 5.6 Взаимодействие фронтенда и бэкенда

Браузер загружает интерфейс и отправляет запросы к API через HTTPS. Данные передаются в формате JSON. Фронтенд не подключается к базе данных напрямую. В первой версии страницы и API предлагается размещать на одном домене; сервер Go может отдавать файлы интерфейса и обрабатывать запросы с префиксом `/api`.

Для входа предлагается серверный сеанс с идентификатором в cookie с атрибутами HttpOnly, Secure и SameSite. Изменяющие данные запросы защищаются от CSRF. При выходе сеанс аннулируется; при истечении сеанса интерфейс предлагает повторный вход. Пароли хранятся только в виде защищённых хешей, как указано в разделе 6.

| Группа API | Назначение |
| :--- | :--- |
| Авторизация | Вход, получение сведений о текущем пользователе и выход. |
| Задачи | Получение доступного списка с фильтрами, просмотр карточки, создание и редактирование задачи. |
| Назначения | Добавление и снятие исполнителей руководителем; начало и завершение своего назначения работником. |
| Подтверждение и отмена | Отдельные действия руководителя с проверкой текущего состояния задачи. |
| Справочные данные | Получение сотрудников для назначения, участков и типов работ. |
| История и сводка | Получение событий доступной задачи и общей статистики для руководителя. |

После действия пользователя сервер проверяет права и данные, выполняет операцию и возвращает результат. Фронтенд обновляет карточку или повторно загружает список. Данные других пользователей обновляются при открытии страницы или ручном обновлении; постоянное соединение и обмен в реальном времени для MVP не требуются.

При ошибках API возвращает HTTP-статус и понятное сообщение: 400 — некорректные данные, 401 — требуется вход, 403 — нет прав, 404 — объект не найден, 409 — действие конфликтует с текущим состоянием, 500 — внутренняя ошибка. Технические детали ошибки пользователю не раскрываются. Конкретные адреса методов и состав JSON-полей фиксируются при разработке API.

#### 5.7 Развёртывание и ограничения реализации

Для демонстрационного стенда достаточно одного экземпляра сервера Go и одной базы данных. Статические файлы фронтенда размещаются вместе с серверным приложением. Для внешнего доступа настраивается HTTPS; параметры подключения к базе, адрес запуска и секреты задаются конфигурацией окружения, а не в исходном коде.

Схема базы создаётся миграциями. Для демонстрации подготавливаются учётные записи, справочники и примеры задач. Инструкция запуска описывает настройку окружения, создание базы, применение миграций и запуск сервера.

Микросервисы, брокер сообщений, отдельный кеш и автономный режим в MVP не требуются. Приложение работает при наличии соединения с сервером.

### 6. Нефункциональные требования

Ниже приведены предлагаемые ограничения учебного MVP. Язык серверной части — Go. Условия измерений, выбор СУБД и окончательный набор инструментов фронтенда уточняются перед реализацией.

| ID | Требование и способ проверки |
| :--- | :--- |
| NFR-01 | Работа в стабильных версиях Chrome, Firefox и Edge, выбранных на дату приёмки. Номера версий фиксируются в протоколе тестирования. |
| NFR-02 | Адаптация интерфейса для компьютеров и смартфонов. На ширинах 360 и 1366 пикселей основные формы и операции доступны без обрезки элементов. |
| NFR-03 | Передача логина, пароля и данных приложения через HTTPS на развёрнутом стенде. |

| NFR-05 | Серверная проверка роли и назначения при каждой защищённой операции. Запросы работника к чужим задачам и операциям руководителя отклоняются. |

| NFR-08 | Русскоязычные интерфейс, сообщения об ошибках и наименования статусов. |

### 7. Границы MVP

В MVP входят авторизация, две роли, создание и ручное назначение задач, индивидуальное выполнение, контроль общих статусов, история и базовые числовые сводки.

В MVP не входят автоматическое распределение, анализ загрузки работников, NDVI и датчики, управление поливом, погодные интеграции, push-уведомления, модуль ремонта оборудования, календарь с drag-and-drop, сложная аналитика и экспорт отчётов в PDF или Excel.

Отдельный мобильный клиент, самостоятельная регистрация и интерфейс администрирования учётных записей не предусмотрены в предложенной версии. Управление справочниками через интерфейс также не входит в описанные функциональные требования.
